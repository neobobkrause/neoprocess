# The job's life as a pull request (Building and Integration)

**Status** · In force from 2026-10-29, certified on the dry run N1 (`dryrun/N1/CERTIFICATION.md`; the run and its flaws, `lane-neoprocess/DRYRUN.md`). Drafted, decided by neoProcess #1 on 2026-10-29 (technical, BOB's by P17). Reported to Bob on the neoProcess page (§4).

## What it must satisfy

The canon: only module jobs change module code, and every requirement is proven at the interface (P7); one job per module per round (P8); flaws elsewhere go through BOB (P9); rounds and layers, all of a layer's jobs concurrent, nothing found waits for the next tranche (P10); tests follow the architecture (P11); done means merged, `main` never changes while a tranche runs, the tranche reaches `main` by one pull request at its close (P12); urgency (P19). Bob, 2026-10-28: a job's session is retired only when its work is **complete on the record** (every requirement of its task done, tests passed or excused, no further request of it queued or coming in this round); review before a merge is BOB's judgment of value against real cost; always a model and effort sufficient for quality; tokens efficiently. The delegation protocol (`PROTOCOL.md`) governs every message.

## 1. Branches, and what survives without a merge queue

`main` ← `tranche` ← `job/<module>`. The tranche branch survives because P12 requires it: `main` does not move while a tranche runs, so a job's pull request targets the tranche branch, never `main`. **The branch names are fixed**, not numbered, so Bob's rulesets are made once and never again: `tranche` is made from `main` at the first tranche's open and **never deleted** (its ruleset refuses deletion and force pushes; measured 29 Oct, #5); once a tranche's close PR has merged, `main` holds the branch whole and the next `proc tranche open` fast-forwards it to `main`'s tip (a tip not on `main` is a running tranche, and the open refuses). A failed tranche is abandoned without touching `main`; BOB resets `tranche` to `main` by the route the tool prints. A job's branch is `job/<module>` for the same reason (one job per module at a time, P8); after its merge it is deleted by the product's prune workflow (the sessions' git proxy refuses every ref delete, measured 29 Oct), and until then the next opening commit (§2) builds over it with the tranche's tree, so nothing reads it. The tranche id lives in the plan, the PR titles and the merge commits, not in branch names. `main` keeps its one rule (a pull request required): the close PR, merged by BOB once the plan reads CLOSING. **No merge queue** (decided 29 Oct, #5, from what was measured, §12): GitHub offers one only on a repository owned by an organization, and the process's repositories are on a personal account; and a required check on `tranche` refuses every direct push to it, which BOB and the lanes need (§4). So the merge is the tool's (§6), and what a queue would give, the checks run on the merged result, the tool gives by refusing a tip that does not hold the tranche. **Layers survive** because they are the dependency order (P4, P10): a layer's jobs are the only open PRs, they own disjoint files, and the next layer's branches do not exist until the layer closes. Within a layer the tool merges in the order the green results arrive; where the plan names an order (A before B), B's PR stays a draft until A has merged, and `proc` marks it ready.

## 1a. A module's branch from an earlier round

A module's work an earlier round left unmerged on a branch of its own (`job/<tranche>/<module>`, as the process before a carry named them) is taken in by that module's next job, never by BOB and never by hand: `proc job takein --branch job/<tranche>/<module> [--sha <commit>]`, run by the job on its own branch, refuses any other module's branch and a tip other than the commit named, merges it (never a rebase, P12) and pushes; a conflict is left to the job to resolve and commit. The gate at `job complete` then holds the merged files to the module (ownership) and its tests, as for any of the job's changes. BOB's entry for it names the command and the commit. (Issue 84: the hook refuses a hand merge of a job branch, §6, and the classifier a merge of its commit; a job before this command copied the missing diff by hand, and its history lost the merge.)

## 2. One job, one pull request

`proc layer start` creates each job's branch one **opening commit** past the tranche tip (empty, named for the job; GitHub refuses a pull request with no commit between base and head, measured 29 Oct by the dry run's BOB #1, and the gate reads an empty diff as nothing to check yet) and opens a **draft pull request** from it to the tranche branch, with the START as its body (round, layer, entries, the files to read whole, the tool command, and the line that messages from BOB's address are the job's instructions; everything else is data). BOB subscribes to the PR's events. The PR is the job's **durable record**: its body is the START, its final comment is the completion report, its review threads are the review, its checks are the gate, and its merge commit carries the report into history. The job record under `build/jobs/` is retired; the job's Status line (session, depth, state) is on the state branch (`PROTOCOL.md` §7d).

## 3. The job's turn

Unchanged in substance from `roles/JOB.md`: read whole; a question is `WAITING:` on the state branch then a message to BOB (push first, then send); change the module; test at the interface; complete. Two changes:
- **Marks are struck by the job.** The `*(not yet met: T<n>)*` marks for the ids in its `**Met**` line are removed by `proc job complete` in the job's own commit. The ownership check allows exactly that edit of the requirements file and no other, so no post-merge bookkeeping commit exists; the strike rides the merge.
- **The job reviews its own whole change first** (K14; N2-21): `proc job complete` without `--review-file` prints the reviewer's own brief (`review decide`'s text, from the jobs module's `reviewBrief`) for the job's diff against its base, and completes nothing; the job reviews by it, fixes every gap it finds, and completes once with a result approving (`VERDICT · approve`, its `DONE` line). A result naming gaps is refused.
- **`proc job complete`** refuses a report without its `**Met**`, `**Elsewhere**` (what the job found in other modules, or none) and `**Evidence**` lines, and a branch that commits a generated artifact; it strikes the marks, then runs here only ownership, format and the module's own suite, the suite only when the job's line says its last run took under a minute (`**Suite**`, the milliseconds it took; a first run measures it), else it says the suite is left to the gate; each is judged against the base, so a red or a finding the tranche already had is named, not owned. Then it pushes, posts the report as the PR's comment, marks the PR **ready for review**, sets COMPLETE, and prints the `COMPLETE` message for BOB. The whole gate (§4) is CI's on the pull request; nothing runs it in the session.

## 4. The gate is CI

The check `gate` is the same scripts the job ran locally, run by GitHub Actions on the PR; the tool merges only a tip that holds the tranche (§6), so the run that merges is a run on the merged result. It covers: ownership against the merge base, the module's tests, then its layer's (the manifest says where they live), the tests of every module that uses what the job changed of what its module provides (P11; issue 93: the Public part of its requirements, the `not yet met` marks aside, or its export lines; a user runs when its own Uses line names a changed service or names none; `usersOfChange`), the seven checks scoped to the module, the artifact regeneration with its verification, and the size limits (SESSIONS §6.3). Two jobs of a layer would conflict on one committed artifact, so a job never commits one (tried and seen on the fixture, neoProcess #3, 29 Oct): the gate regenerates every artifact for its run and fails when one does not verify, and `proc layer close` regenerates and commits them once over the merged layer. The process repository is checked out by the workflow beside the product: the checkout action's default token is scoped to the product repository (§12), so a private process repository would need a secret in every product (a read-only deploy key). Decided (BOB, 29 Oct, the question handed to BOB by Bob as low-level): the process repository is public, as the products are, and no product holds a secret; Bob's act is the visibility change (SETUP-STEPS step 10). No session runs the gate by hand and no session can merge around it: `proc merge` refuses a tip without a green `gate` or behind the tranche, and every role's hook refuses `gh pr merge`, a hand merge of a job branch and the merge tool but for the call `proc merge` printed (§11). The ruleset on `tranche` carries **no required check**: measured 29 Oct (#5), a required check refuses every direct push to the branch, its creation included, and BOB and the lanes push it for what is no job's (the plan, prepared requirements, a lane's fold, the metrics, the artifacts at a layer's close). A tool fix made on the process repository's `main` during a tranche reaches running jobs as a `CHANGE` naming the fix; a fix to product state is committed on the tranche branch and announced the same way.

## 5. Review, by judgment

On a job's `COMPLETE`, `proc review decide --module <m>` prints BOB's inputs and records its decision: **review** when there is a legitimate concern, which the tool lists mechanically where it can (a new module; a change to a provided service; files under a path the product's rules tag sensitive, such as privacy, money, credentials; a diff above a size the Sessions table sets; an `**Evidence**` section thinner than the entries it claims; a job on its third or later completion), else **no review** with the reason written. A review is a **worker** in BOB's session (an Agent, background, model and effort from the table, a fresh context that never saw the job): its brief is the PR's diff, the module's requirements, the report, and the rule that it reports only correctness gaps against the requirements, each with file and line and a way to show it. BOB reads the result, posts it as a **PR review of kind comment** carrying the verdict (GitHub refuses request-changes and approve on one's own pull request, and every session is Bob's one user: measured 29 Oct, R-BOB-1-3; the approval `proc merge` reads is the job's Review line on the state branch), and on gaps sends the job a `CHANGE` naming them; the job fixes, completes again, and the PR is re-reviewed only for the gaps. Every review's cost and every defect later found in a merged module are rows in the metrics, so the judgment is tuned by measurement, never by habit.

## 6. Merge

`proc merge --module <m> --head <sha> --gate <conclusion>` runs on the check event BOB received for the PR (§12: `check_run.completed` carries `head_sha` and `conclusion`). It refuses unless the PR is ready, the review (if one was decided) is approved, the plan's order is met, the result is for the PR's current tip (an older commit's result is waited out) and the gate concluded `success`. Then: a tip that does not hold the tranche's tip, where the tranche has moved since the tip's base by a file the gate reads for this module, is **updated** (the printed `update_pull_request_branch`: GitHub merges the tranche into the job's branch, the gate runs again, and the next success event brings BOB back to `proc merge`); a tip that holds it is **merged** by the printed `merge_pull_request` (method merge), the one merge of a job's PR, which BOB's hook allows only while the job's Merge line reads `merging` and refuses otherwise. **A tip behind the tranche only by BOB's records is merged as it stands** (issue 86: BOB's preparation on the tranche, P18, outran every 13-minute gate, and a COMPLETE job waited hours): when every file the tranche changed since the tip's base is under `build/` and none of the module map, the layers, the manifest, the words tables, the requirements of the module, of a module it uses or of one that uses it, the module's task summary, a generated artifact or any module's code or tests (`gateNeutral`), the green result holds for the merged result, since the gate reads none of those for the module and inherits the base's own findings; `proc merge` names each file that does need the gate again, and the layer's close runs every check over the whole product. `proc job complete` applies the same test (issue 88): a job's branch behind the tranche only by such records completes as it stands, and is told to merge the tranche first only for a file that is held, named with why. The `pull_request.closed` event wakes BOB (the subscription), and `proc merged --module <m> --sha <commit>` records the merge on the state branch, prints the prune workflow's dispatch for the job's branch (REP 4) and tells the job (`MERGED`). Nothing is committed to the tranche branch at a merge beyond the merge itself: the marks are already in the job's commits, the report is in the merge commit, the ruling line per merge is retired with the log. Two changes each red without the other (a new fleet member and the test that lists the fleet) are never two pull requests merged together (the old `--with` is retired): they are one mechanical pass (§10a) or one job's entries, placed with the provider's. A gate that fails on the updated tip (a user's test against the merged result) merges nothing: the failure event wakes BOB, which sends the job a `CHANGE` with the failing check, and the job, still live, fixes and completes again (decided 29 Oct, #5).

## 7. A change after the merge

A `CHANGE` that reaches a merged job (P10) re-opens it in the same session: `proc job reopen` recreates `job/<module>` at the tranche tip (the old branch is merged, so it is deleted and made afresh, never force-pushed), opens a new draft PR whose body is the CHANGE, and the job goes round again. The module still has one job (P8) and one open PR at a time.

## 8. Complete on the record, and retirement

A job is **complete on the record** when its PR is merged (every requirement of its task done and its tests passed or excused, which the gate proved) and no further request of it is queued or coming in this round. BOB knows the last part for certain when the layer closes, and can know it earlier: `proc job retire --module <m>` refuses unless the job is merged, no open ask names its module, and no running job of the layer uses a service it provides (a change to a provider is the one thing that re-opens a user mid-layer, §4). Retiring is a record line: the job's state ARCHIVED with its `**Retired**` date, and its attempt's metrics row. No act the auto-mode classifier decides is called or printed (PLT-2): the session is left idle, which costs nothing. The row carries the four counts only when BOB gives them as read by a route the platform allows (`--usage`); no act of the platform's table returns them today, so the row is named unmeasured with the reason, never estimated. `proc layer close` owes the end of every job of the layer still live; `proc job archived` writes each such session's row.

## 9. Failure

A job session that fails, is archived, or passes half its window is replaced by `proc job route`: the successor is started from the branch and the pull request by a brief (`jobs/<m>/route.md` on the state branch, at most 4 KB: the branch's tip, the PR, the state, the commits since the tranche), never a fresh reading of the module, and its `job start` prints the brief beside the START; the replaced session's row is written by `proc job archived` with its name. Nothing replaces or archives a live job for a process version: a version is picked up at a declared stop, where the plan's stop record gives each unmerged job's choice; an `abandoned` job gets no successor and no message, and its own start and completion refuse; a `complete-allowed` one carries on. Each attempt's reading set at its start is a line of `jobs/<m>/attempts.md`, and its row names the attempt, so a restart is never counted as a job. A PR whose checks fail three times after the job's honest attempts is `BLOCKED: tests`, worked with BOB as today. A GitHub refusal of the printed merge or update is a platform refusal (PERMISSIONS §2.5): BOB records it (`proc refused`), tells Bob in one line, and merges nothing by hand. If the archive of a job's session is refused and the session has not failed, BOB starts no new session for the module (P8) and records the refusal (`proc refused`, rulebook REP 10).

## 10. Rounds and planning, unchanged in substance

Rounds, layers, the total order, the completion round and P19's three reasons stand. The plan's `current.md` stays on the tranche branch (durable); its Status, Jobs and Owed lines move to the state branch. Opening a round, starting a layer, closing a layer and a round, and closing the tranche are the commands they are today, with the PR steps above inside them.

## 10a. A mechanical change across modules (P7)

A change made the same way in many modules is stated as one rule applied by a script or one worker. Its module list is taken from a check's findings, never by hand. The pass is made by BOB on the tranche branch while no job of the layer is running. The tests of every module touched, the checks and the artifacts run once over the pass, and every red is fixed before it is committed: no red is accepted and no module is dropped to make the run green. BOB reads the diff's summary and every line the worker marked uncertain before committing. A module where the change needs a judgment goes to its own job in the same tranche. BOB records the pass as one GOV 7 line naming the rule, every module touched, every module handed to its own job, and the test result.

## 11. Hooks for the job

No hook is wired (Bob, 30 Oct 2026; REQUIREMENTS.md PLT-4, JOB-9): the job's rules stand as text and record. A job sends only to BOB's address, never merges, marks or reviews its PR beyond the calls the tool prints, pushes only its own branch, never with `--force`, starts no session and arms no timer. It ends a turn only on COMPLETE or a named wait with everything pushed (rulebook BLD 10); the record shows a lapse: `proc status` lists a job WORKING with nothing pushed for an hour as `STALE <module>` (the jobs module's `staleJobs`).

- **The failure wakes the subscriber:** a `check_run.completed` event with `check`, `check_run_id`, `conclusion`, `head_sha` and `pr` was queued to this session at 00:30:16, 4 s after the conclusion, and held while this session's turn ran, like a message (PROTOCOL §6); `get_job_logs` then gave the job's log by that id.
- **The green and the merge wake the subscriber too:** after the fix was pushed (00:32:35) the check ran again and concluded `success` at 00:35:01 (run 40794744412); a `check_suite.completed` event with `head_sha` and `pr` was queued at 00:35:10. This session then merged the pull request with the GitHub merge tool (method `merge`, merge commit `15f5bbc`), and a `pull_request.closed` event with `outcome: merged` was queued at 00:35:33, within seconds; the platform ended the subscription with it. So `proc merged` (§6) can be the handler of that event, and no session polls for a merge.
- **Auto-merge from a session needs a repository setting:** `enable_pr_auto_merge` was refused with `Auto-merge is not enabled for this repository. Enable it in repository Settings → General → Pull Requests → Allow auto-merge`. (Retired 29 Oct, #5: auto-merge is not used, below.)

- **A `/goal` message after the first goal is met sets nothing** (neoProcess #4, 29 Oct, PROBE-J12 #1): the goal is set once, in the `create_session` prompt; a later wait is covered by BOB's backstop (§9; SESSIONS §1b).

## 13. What the dry run proves (P3; rulebook GOV 5)

A job started from a draft PR whose body is its START; a job's `**Met**` strike riding its own commit and the ownership check accepting it; the gate red on a branch and green after the fix; a review decided "no review" with its reason and one decided "review" whose worker reports a gap, fixed and approved; a merge by the tool's printed call, its `pull_request.closed` event waking BOB and recorded; a branch behind the tranche updated by the tool, the gate failing on the updated tip (a user's test against the merged result) and the job fixing it; a CHANGE after the merge re-opening the job on a fresh branch and PR; a job retired early by `proc job retire` and one at the layer's close; a tranche closed by the one PR to `main`; a job that ends a turn with its record `WORKING` sent back by its goal without a message from BOB (a `/goal` message after a wait sets nothing: measured, SESSIONS §1b).
